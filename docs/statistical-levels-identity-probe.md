# Statistical Levels identity probe

`PROBE_IDENTITY` is a separate non-release operation in `.github/workflows/statistical-levels-release.yml` on `vercel-deployment`. It accepts only `probe_git_sha` and `probe_deployment_id`; the existing release inputs must be empty. No URL, role, project, service endpoint or Lambda name is accepted from the operator.

The probe resolves the immutable Preview using public GitHub metadata from the fixed Vercel integration. It selects the latest commit status for the supplied deployment ID, then requires the latest corresponding Preview deployment status to match the SHA, trusted creator, timestamp and exact origin links. A later Production deployment cannot replace the chosen Preview. No `deployments: read` permission or GitHub token is needed for these public reads.

Execution source and fixture source are separate checkouts. The workflow verifies its frozen helper hashes before running helpers, independently checks its GitHub execution identity and fixture ancestry, and verifies the fixture's pinned source files, 81 snapshots, provenance and 87-capability ledger. A probe records the fixture's authority as QA evidence; it never selects authority for publication. ADOPT and PROMOTE retain their existing validation, including PROMOTE's future-authority requirement and their unchanged controller request schemas.

Only after an affirmative anonymous protection baseline, protected QA requests a short-lived GitHub OIDC token for `https://github.com/luiguiHerrera`. The token is held in memory and attached only to the verified Preview origin using `x-vercel-trusted-oidc-idp-token`. Cross-origin redirects are refused; bypass secrets, Vercel administrative tokens and Founder browser sessions are not used.

The direct `identity-probe` job has no GitHub Actions `environment` and no reusable-workflow boundary. Its Vercel and AWS tokens must both have the exact branch subject `repo:luiguiHerrera/Luiguiherrera-web:ref:refs/heads/vercel-deployment`. Vercel's target environment `Preview` does not create a GitHub job environment. Unexpected token `environment` remains forbidden. Exact issuer, audience, repository and immutable IDs, ref, caller workflow ref/SHA, execution SHA, workflow name, event, run ID/attempt, RS256 signature, key and time checks remain mandatory.

The current security policy is `JOB_WORKFLOW_IDENTITY_MUST_MATCH_EXACT_JOB_DEFINITION`. Each OIDC-validation step receives only four explicit native values: `job.workflow_ref`, `job.workflow_sha`, `job.workflow_repository` and `job.workflow_file_path`. They are passed at `steps.env`, where GitHub permits the job context; complete contexts are never serialized. The native job ref/SHA/repository must equal the independently qualified caller `GITHUB_WORKFLOW_REF`, `GITHUB_WORKFLOW_SHA` and `GITHUB_REPOSITORY`, and its path must equal `.github/workflows/statistical-levels-release.yml`. The caller SHA must also equal `GITHUB_SHA`. Both token `job_workflow_ref` and `job_workflow_sha` must be present and equal those exact native job values. Missing or mismatched claims fail with separate codes. Any native job/caller divergence fails as `UNEXPECTED_REUSABLE_OR_ALTERNATE_JOB_WORKFLOW_IDENTITY`; arbitrary reusable workflows are not accepted. See GitHub's [job context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#job-context), [context availability](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#context-availability) and [September 3, 2026 updates](https://github.blog/changelog/2026-09-03-github-actions-early-september-2026-updates/).

The application and exact fixture source both render `/` and `/niveles-estadisticos` directly. Proxy canonical mappings write Link metadata, not redirects. The preflight retains `/niveles-estadisticos`. It first performs an anonymous GET with manual redirect handling and no token request. Anonymous redirects can be followed at most twice under the same strict exact-origin HTTPS path policy, without any credentials. The resulting baseline has exactly three semantic outcomes:

- `PROTECTED`: a recognized HTTPS Vercel authentication redirect with status301/302/303/307/308 positively identifies protection. A generic3xx,401 or403 is insufficient. Only this outcome permits the Vercel token factory to execute.
- `PUBLIC`: anonymous2xx HTML contains the actual parsed initial Statistical Levels SSR structure and exact localized heading on the verified fixture route, directly or after safe anonymous redirects. Stop with `BLOCKED_PREVIEW_NOT_DEMONSTRABLY_PROTECTED`; token creation, trusted requests, browser QA and AWS are unreachable.
- `AMBIGUOUS`: anything else, including unknown redirects,5xx, empty/unverified content and transport anomalies. Stop with `BLOCKED_ANONYMOUS_PROTECTION_BASELINE_AMBIGUOUS`; the same downstream operations remain unreachable. Available status/Location and the distinct diagnostic cause remain recorded.

`probe-gate.mjs` persists the positive baseline before a lazy callback can request Vercel OIDC. The probe-only token budget permits exactly one initial certification acquisition and no certification refresh. That token is reused through the existing safe same-origin redirect chain for `/niveles-estadisticos`. When this first route reaches verified fixture content, an immutable sanitized HTTP receipt is persisted and the budget records Trusted Sources certification before the separate QA phase becomes reachable. The English preflight and browser QA occur after that checkpoint. Both canonical trusted preflights must reach verified fixture HTML before the shared browser harness and rendering execute; the probe-specific product runner then opens the real guide and verifies the exact authority field in Chromium. The shared ADOPT/PROMOTE runner stays unchanged. The V3 OIDC validator and native job/caller identity model remain unchanged.

The existing usable-token invariant is `exp > now + 30`. A newly acquired token that cannot satisfy it fails closed without acquiring another certification token. A token with 45 seconds remaining remains usable; the former shared lease's proactive `<=60` refresh trigger is not used by the probe. That former helper performed at most one refresh per getter call, but later getter calls could renew again: it had neither a phase boundary nor a per-run budget. It did not intentionally mint one token per redirect, and did not loop within one call until a long-lived token arrived. The shared release helper remains byte-identical.

After certification, the same token is preferred while it remains usable. Only when remaining validity is `<=30` may QA request one replacement for the same fixed Vercel audience and exact verified Preview origin. Concurrent lease reads share the acquisition. A second renewal requirement fails as `BLOCKED_QA_OIDC_REFRESH_BUDGET_EXCEEDED`; a too-short replacement or failed acquisition also fails without retry. Total Vercel acquisitions are therefore bounded by one certification request plus zero or one QA refresh. AWS-audience requests are separate and do not consume this budget. No token or token fingerprint is included in the phase journal. These limits apply only to `PROBE_IDENTITY`; ADOPT/PROMOTE credential lifecycles are unchanged.

Each HTTP response is journaled before a routing decision. The journal stores exact status; Location presence, scheme, host, path, query/fragment presence and relative/same-origin/cross-origin class; and only `server`, `x-vercel-id`, `x-vercel-cache`, `x-vercel-error` when their values satisfy explicit non-secret formats. Unknown or credential-shaped host/path/header data is redacted; unsafe host/path data is retained only as a hash. Location query values, fragment values, userinfo, raw URLs, cookies and response bodies are never journaled. No query key names are retained.

Trusted redirects may be manually followed at most twice, using the exact verified HTTPS Preview origin and an ordinary application path with no userinfo, port change, encoded/dot-segment path, query or fragment. Rejecting all query/fragment redirects is deliberately stricter than attempting to distinguish safe query values. Every trusted hop explicitly reissues the OIDC header. Cross-origin destinations are classified and never followed; loops and excess hops fail. This policy is local to the identity probe; shared release transports and ADOPT/PROMOTE jobs are unchanged.

A generic 3xx remains inconclusive. Matching anonymous/trusted redirects to an explicitly recognized Vercel login target produce `BLOCKED_TRUSTED_SOURCES_LIVE_CONFIRMED`; unknown Vercel destinations remain platform redirects. HTTP 303 alone is not a readiness diagnosis. The documented `DEPLOYMENT_NOT_READY_REDIRECTING` error together with 303 is classified as a readiness inconsistency against the fixture's verified Ready metadata. No configuration change, fallback credential or retry follows any failure. See Vercel's [deployment-not-ready redirect documentation](https://vercel.com/docs/errors/DEPLOYMENT_NOT_READY_REDIRECTING).

The probe uses three independent layers. Layer1, Vercel protection acceptance, requires an affirmative protected anonymous baseline and a trusted2xx response from the exact verified Preview origin without a Vercel platform-error header or implicit transport redirect. This status-level acceptance does not establish application content. It remains true if the later HTTP fixture or browser product/authority stage fails. The Founder accepted this protection-layer certificate for run `34692322880`: anonymous302 protection, trusted200 after the Custom explicit-claim rule, signed V3 OIDC and all six exact Custom claims. That historical run still failed HTTP binding under the invalid initial `sl-controls && sl-authority` predicate; no browser QA or AWS certificate is inferred.

Layer2 binds the immutable public deployment metadata (exact origin, deployment ID, Git SHA, project and Preview environment), requested route,2xx and HTML content type to parsed initial SSR. Both routes require exactly one `div.sl-page`, its direct `div#sl-controls.sl-controls`, and its direct `header.sl-heading > h1` containing one text node with the exact localized heading. Final paths must equal the requested route, optionally with its canonical trailing slash. Comments, script/JSON strings, inert containers, generic/platform HTML, duplicate controls and wrong-language/route headings cannot pass. Each marker has its own diagnostic. The parser is a locally pinned upstream bundle; no network parsing service or application dependency is added. `sl-authority` is an optional initial-DOM diagnostic only. Authority substring matching is removed from every PROBE PASS path.

The second marker comes from exact fixture `4ee6adb006f360fea13837db5f7d45815f297b55`, `components/statistical-levels/StatLevelsLab.tsx`, direct heading at lines57–59: ES `¿Dónde está este activo frente a su propia historia?`; EN `Where is this asset relative to its own history?`. Layer3 uses Chromium through the unchanged read-only harness. On each exact language route it issues a real click on `#sl-guide > summary`, waits for the guide to open and mount the single `div#sl-authority.sl-provenance`, then reads the first direct `p.break-all` in its single direct `details` child. The structure must contain exactly the two expected direct `p.break-all` fields, and the baseline field must contain one text node. This is the legitimate `asset.dataAuthority.baselineId` field rendered by `StatLevelsLab.tsx`; the second field is the raw manifest hash. Comparison uses strict text equality to the fixture's provenance authority, with no trim, substring, prefix or suffix acceptance. For the exact fixture the expected authority is `20260908T125656658Z-a4743804-e5f1-495a-b34e-5948d5db4d2d`. Observed page values are never serialized into diagnostics. A missing, malformed or mismatching field fails closed.
